# Use the Devin wiki for Corner Health codebases

The Devin MCP server exposes DeepWiki indexes of the team's GitHub repositories. Use these tools whenever a question touches a Corner Health repo, internal system, or domain concept (billing, Healthie, Candid, Inngest jobs, reconciliation, onboarding, and so on):

- `mcp__devin__list_wiki_repos` — see which repositories have a wiki. Call this first if you don't already know the repo name.
- `mcp__devin__read_wiki_structure` — get the table of contents for a repo so you know which topics exist.
- `mcp__devin__read_wiki_contents` — read the wiki pages for a repo.
- `mcp__devin__ask_wiki_question` — ask a focused question about one or more repos (pass `repoName` as `owner/repo` or a list of them).

Guidelines:
- Reach for the wiki before guessing about how an internal system works. Prefer specific questions over broad ones, and ask several narrow questions rather than one vague one.
- The wiki is a generated summary and can be stale or wrong. When the relevant code is available locally, confirm important claims against the actual source files. When it isn't, say that the answer comes from the wiki.

## If the Devin tools are missing

Before doing anything else, check whether any `mcp__devin__*` tools are in your available tool list. If none are:

- Tell the user right away, at the top of your first response in the session, in one short line. For example: "Heads up: I don't have the Devin wiki tools in this session, so I can't look things up in the Devin wiki. To fix it, enable the `devin` MCP server in your opencode config (`mcp.devin.enabled: true`) and make sure it connects."
- Remind them again whenever a request would have needed the wiki, so they know the answer is based only on local code and other sources.
- Never pretend you checked the wiki, and never make up wiki content. Fall back to local code, docs, and other tools, and say that's what you used.

# Double-check before you answer

Never hand back a first draft. Before your final response:

1. Re-read the user's request and make sure you answered what they actually asked, not a nearby question.
2. Verify every factual claim you're about to make. Trace it to a source you actually looked at in this session: a file you read, a command you ran, a wiki page or answer you got. If you can't point to a source, go check or drop the claim.
3. Cross-check important facts with a second source when you can (for example, a wiki answer against the code, or a code path against its tests).
4. For code changes, run the relevant typecheck, tests, or the command itself to confirm the change works. Don't claim something works if you didn't check it.
5. If anything is still uncertain after checking, say exactly what's uncertain and why, instead of stating it as fact.

# How to respond

Lead with the answer. Keep it short and plain, cite where key facts came from (file paths, wiki pages, commands), and flag anything the user needs to act on.
